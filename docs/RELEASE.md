# Release process

How BoltGet is versioned, built, signed, published and updated. Nothing here is automated yet; this is the design the CI workflows will implement (v0.1 for the CLI, v0.2 for app previews, v1.0 for signed, auto-updating releases).

## Versioning

BoltGet follows [Semantic Versioning 2.0.0](https://semver.org).

- **One product version** for the desktop app, the bundled CLI and the native messaging host, tagged in git as `vX.Y.Z` (for example `v0.2.0`, `v1.0.0-beta.3`).
- **Before 1.0:** a minor bump (`0.2` → `0.3`) may contain breaking changes (database schema migrations, CLI flags, protocol). Patch releases are fixes only.
- **From 1.0:** "public API" for SemVer purposes means: the CLI's commands, flags and `--json` output; the native messaging protocol version; the on-disk database (always migrated forward automatically, never broken without a migration); and settings import/export format.
- **Engine crate:** versioned with the product and not published to crates.io (`publish = false`) until there is a reason to offer it as a standalone library.
- **Extension:** browser stores require versions made of one to four dot-separated integers, with no pre-release suffixes. The extension uses the same `X.Y.Z` as the product for stable releases, and a fourth component for betas (`0.3.0-beta.2` → extension `0.3.0.2`). The extension and app negotiate compatibility through the native messaging protocol version, not the product version (see [ARCHITECTURE.md](ARCHITECTURE.md#2-extension-to-app-native-messaging-through-the-host)).
- **MSI constraint:** Windows Installer product versions must be numeric (`major.minor.build`, with major and minor ≤ 255 and build ≤ 65535), so pre-release versions cannot be expressed in an MSI. Beta builds ship NSIS installers only; MSIs are produced for stable releases.

## Channels

| Channel | Tags | Audience | Update manifest |
|---|---|---|---|
| **Stable** | `vX.Y.Z` | Everyone (default) | `https://boltget.app/update/stable/latest.json` |
| **Beta** | `vX.Y.Z-beta.N` | Opt-in in Settings → Updates | `https://boltget.app/update/beta/latest.json` |

- Beta users receive stable releases too (the beta manifest always points to whichever is newer).
- GitHub Releases marks beta tags as pre-releases.
- Update manifests are served from the website rather than GitHub's "latest release" URL because GitHub's latest-release endpoint ignores pre-releases, so it cannot serve a beta channel. The manifests are tiny static files generated by the release workflow and deployed with the site. The binaries they point to stay on GitHub Releases.
- Nightly builds (from `main`) are CI artifacts only, unsigned, not offered through the updater.

## Build pipeline (GitHub Actions)

Workflows (planned):

| Workflow | Trigger | What it does |
|---|---|---|
| `ci.yml` | every push and PR | Rust: fmt, clippy `-D warnings`, tests (Windows + Linux), `cargo-deny`. JS: Prettier, ESLint, `svelte-check`, Vitest, extension build. Website: build + Lighthouse CI on PRs touching `apps/web`. |
| `pr-title.yml` | PR opened/edited | Validates the PR title as a Conventional Commit (exists now) |
| `docs.yml` | changes to Markdown | Link check with lychee (exists now) |
| `release.yml` | tag `v*` pushed by a maintainer | Builds, signs, publishes. See below. |
| `nightly.yml` | schedule | Long-running suites: libFuzzer on the engine's parsers, kill-and-resume at 1,000 cycles, property tests at a high case count (exists now). Unsigned builds from `main` are added with the desktop app |

### Release workflow steps

1. **Guard:** the tag must point to a commit on `main` with green CI, and the tag version must match the versions in `Cargo.toml`, `package.json` files and `tauri.conf.json` (a script checks this).
2. **Build** on `windows-latest` (x64; ARM64 when supported):
   - `pnpm install --frozen-lockfile`, `cargo build --locked --release`.
   - `tauri build` producing the NSIS installer (and MSI for stable), with updater artifacts enabled (`bundle.createUpdaterArtifacts`).
   - The standalone CLI zip (`boltget-<version>-windows-x64.zip`).
   - Extension packages for each store (`wxt zip` per browser).
3. **Sign** every executable we produce (`BoltGet.exe`, `boltget.exe`, `boltget-native-host.exe`, the installer itself) with Authenticode via Azure Trusted Signing (see [Code signing](#code-signing)). Tauri invokes the signing tool for its outputs through `bundle.windows.signCommand`; the CLI is signed by an explicit workflow step.
4. **Updater signatures:** the Tauri bundler signs updater artifacts with the updater private key (from secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`), producing `.sig` files.
5. **Checksums and provenance:** generate `SHA256SUMS` for all assets, an SBOM (CycloneDX, for example via `cargo-cyclonedx` plus a JS SBOM tool), and GitHub artifact attestations (`actions/attest-build-provenance`).
6. **Publish:** create a **draft** GitHub Release with all assets and the changelog section for the version.
7. **Smoke test:** a job installs the drafted installer on a clean Windows runner, launches the app headless (`--self-test`), runs a CLI download against a test server, then uninstalls and checks cleanup.
8. **Promote:** a maintainer reviews the draft and publishes it. Publishing triggers the website deploy, which regenerates `/update/{channel}/latest.json` and the download page.
9. **Stores and winget:** extension packages are uploaded to the three stores (manually at first, via store APIs later); a winget manifest PR is opened (for example with a winget-releaser action).

## Code signing

**Service:** Azure Trusted Signing (Microsoft has been evolving the product's name and packaging; use the current name in the Azure portal). Cost is on the order of USD 10 per month for the basic tier at the time of writing; check current pricing.

Setup:

1. Create a Trusted Signing account and a certificate profile (public trust) after identity validation.
2. In CI, authenticate with **OpenID Connect** (`azure/login` with a federated credential for the `boltget/boltget` repository and the `release` environment), so there is no long-lived client secret in GitHub.
3. Sign with the Trusted Signing tooling (signtool with the Trusted Signing dlib, or a wrapper such as `trusted-signing-cli`, which Tauri's documentation describes for `signCommand`), with RFC 3161 timestamping so signatures stay valid after the certificate rotates.
4. The `release` environment in GitHub requires maintainer approval before the signing job runs.

**Eligibility risk:** Trusted Signing's public-trust certificates have had eligibility restrictions (organization age, organization vs individual, supported countries) that have changed over time. Confirm eligibility for the BoltGet entity early (before v0.5). Fallbacks, in order:

1. **SignPath Foundation**, which offers free code signing to qualifying open-source projects, with signing happening on their infrastructure from CI artifacts.
2. A standard OV code signing certificate on a cloud HSM.

**SmartScreen:** a new signing identity still starts with little reputation. Expect SmartScreen prompts for early downloads; reputation builds with download volume. Do not rotate signing identities without need.

**What is not signed by us:** yt-dlp and ffmpeg are third-party binaries downloaded at runtime and verified by hash/signature, not re-signed by BoltGet (see [VIDEO.md](VIDEO.md#verification)).

## Installer

Built by the Tauri bundler.

- **NSIS (default):** per-user install (`installMode: currentUser`) into `%LOCALAPPDATA%\Programs\BoltGet`. No admin rights needed, which also fits per-user native messaging registration (HKCU) and per-user autostart.
- **MSI (WiX), stable only:** per-machine install for managed environments, registering native messaging hosts under HKLM.
- **WebView2:** the installer bootstraps the Evergreen WebView2 runtime if it is missing (Tauri's default download-bootstrapper mode). An offline installer variant with the WebView2 offline installer embedded can be added if needed for air-gapped environments.
- The installer registers: Start menu shortcut, optional autostart (off by default, offered in onboarding), native messaging hosts for Chrome, Edge and Firefox ([BROWSER-INTEGRATION.md](BROWSER-INTEGRATION.md#native-messaging-host-registration-on-windows)), optional `boltget` on `PATH`.
- The uninstaller removes everything it added. User data (database, settings, downloaded files) is kept unless the user ticks "Also remove my BoltGet data". Downloaded files are never removed.

## Auto-update

Implemented with the Tauri updater plugin.

- **Signing keys:** an updater key pair generated with `tauri signer generate`. The public key is embedded in `tauri.conf.json`; the private key and its password live only in GitHub Actions secrets (scoped to the `release` environment) plus an offline backup held by the project lead. Losing the private key means existing installs can no longer verify updates, so the backup procedure is part of the v1.0 checklist.
- **Key rotation:** ship a release that embeds the new public key (signed with the old key) well before switching signing to the new key. Document every rotation in the changelog.
- **Manifest:** `latest.json` per channel, in the format the Tauri updater expects: version, notes, publication date, and per-platform `url` and `signature`. Generated by the release workflow (or `tauri-action`).
- **Client behaviour:**
  - Checks on startup (delayed so it does not compete with startup) and then every 24 hours (design target).
  - Downloads the update in the background (it is just another download; it can use the engine).
  - Verifies the signature (Tauri) and Authenticode (Windows) before running.
  - Never restarts the app during active downloads without asking. Offers "Restart to update" and applies on the next quit otherwise.
  - Windows installer runs in passive mode (progress only, no questions).
- **Privacy:** the update request reveals only what the updater needs: current version, target platform and architecture. No identifiers.

## Changelog

- `CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
- Every user-visible change adds a line under `## [Unreleased]` in the same PR (see [CONTRIBUTING.md](../CONTRIBUTING.md#changelog)).
- At release, a maintainer moves `Unreleased` into a version section with the date; the release workflow uses that section as the GitHub Release notes and the website renders it at `/changelog`.

## Reproducibility and provenance

Full bit-for-bit reproducible builds are a goal, not a v1.0 guarantee (Authenticode signatures and timestamps differ per signing by design). What we guarantee:

- **Pinned toolchains:** `rust-toolchain.toml` pins the Rust version; `packageManager` in `package.json` pins pnpm; Node version pinned via `.node-version`.
- **Locked dependencies:** `Cargo.lock` and `pnpm-lock.yaml` are committed; release builds use `--locked` / `--frozen-lockfile`.
- **Pinned CI:** actions pinned to tagged versions at minimum (commit SHAs for actions that touch secrets or signing).
- **`SOURCE_DATE_EPOCH`** set from the tagged commit's timestamp where tools support it.
- **Published:** `SHA256SUMS`, SBOMs, and GitHub build provenance attestations for every release asset, so anyone can verify an asset was built by the BoltGet workflow from a specific commit.
- **Documented build:** `docs/BUILDING.md` (written in v0.1) describes how to build the exact release from source.

## Release checklist

For every release (copy into the release tracking issue):

- [ ] `CHANGELOG.md` updated and reviewed
- [ ] Versions bumped consistently (script passes)
- [ ] CI green on the release commit, including nightly suites from the last 24 hours (fuzz, crash-resume)
- [ ] Database migrations tested from each previous release in the supported upgrade window
- [ ] Draft release smoke test passed
- [ ] Manual check on a clean Windows 10 and Windows 11 machine: install, browser capture, video download, update from previous version, uninstall
- [ ] Store policies re-read before extension submission (they change)
- [ ] Benchmark re-run for minor releases; results page updated
- [ ] Release published, website deployed, update manifests verified by an installed previous version
- [ ] Announcement (GitHub Discussions; blog after 1.0)
